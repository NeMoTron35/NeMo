# qli-core contributor rules

- Flywheel scenario math in `flywheel.ts` stays typed "hypothetical"; only `flywheel-live.ts` builds real claim/buyback/burn transactions, each wallet-approved, program-allowlisted and sent once, so allocation splits are never presented as on-chain routing or automation.
- Quantum Authorization intents (`authorization.ts`) are application-level only: they bind the reviewed message hash and live context, fail closed when policy is enabled, and never sign or send Solana transactions, so the wallet remains the sole transaction authority.
- QLi Agent is read-only; proposals reach Flywheel only through validated in-memory handoff and are always rebuilt and wallet-approved.
- QLi Agent v2 owner data is backend-only behind wallet-signed sessions; the scheduled worker is read-only and authenticates with a database-held token, so no browser role or worker can move funds.
- Quantum Vault rules live in the dependency-free policy crate shared by Anchor; builders require recent devnet genesis, executable ProgramData hash and expected upgrade-authority validation, and configuration stays null until owner-controlled deployment is verified, so static config cannot enable unverified writes.
- Vault SBF tests run only with an explicit local artifact opt-in and execute the compiled program through Solana BanksServer; clock/overflow fixture injection is identified separately from reachable transactions, so policy tests cannot be mistaken for deployment evidence.
- The Program Verifier, Vault Sentinel and Identity 2.0 model are read-only/off-chain: verifier reports always carry `writesEnabled: false`, sentinel proposals are non-executable typed documents, and v2 proofs never authorize, so evidence can never silently enable signing.
- Vault monitoring persistence is backend-only and gated by `monitorAvailability(QUANTUM_VAULT_DEPLOYMENT)`; ownership is the signed session wallet matched to the on-chain vault owner, so unverified deployments or typed addresses can never create monitoring rows or alerts.
- `programs/quantum_identity_verifier` is a standalone reference crate (own workspace) mirroring frozen pq.ts bytes; it has no entrypoint and must never be referenced by the vault program, so research crypto cannot become a fund permission.
- Neural/Proof/Shadow/Threat Graph/Arena live in `src/lib/qli-core/neural/`: pure cores are browser-safe, `neural.server.ts` alone reads HF_TOKEN and owner rows after `requireSession`, sends only a locally classified task enum plus numeric address-free evidence after an atomic DB budget reservation per request, and nothing there builds, signs or sends transactions, so model output can never become authority.
- Launch Proof Engine (`launch-proof.ts` pure core, `launch-proof.server.ts` adapters) verifies DBC launches only from server-trusted RPC with derived, DBC-owned, newly created accounts and refuses to guess; receipts are unsigned integrity checksums and intent linkage stays unverified, so proof pages can never sign or overstate evidence.
- Lifecycle Intelligence (`lifecycle.ts` pure core, `lifecycle-sdk.ts` SDK decode/quote, `lifecycle.server.ts` RPC) reads only server-owned RPC after genesis and DBC-owner checks, binds each fetched transaction to its own signature and quotes with SDK `swapQuote2`, so public pool pages can never sign, guess history or substitute the hypothetical Shadow model.
- Creator Studio (`creator-studio.ts` pure core, `creator-studio.server.ts`) drafts only: owner rows are service-role tables scoped by the wallet-signed session, evidence cards come solely from server-trusted lifecycle snapshots and creative copy is never labelled verified, so drafts can never sign, post or overstate chain facts.
- Hook Forge (`hook-forge.ts` pure core, `hook-forge.server.ts` inspector) is read-only: fee math is SDK-parity tested, Token-2022 inspection uses server-trusted RPC with genesis checks and never reports compatibility, and custom hook deployment stays disabled, so policy design can never sign or imply an on-chain hook.
- Hook Forge v2: the research transfer hook (`programs/quantum_transfer_hook`, standalone workspace) only refuses or allows Token-2022 transfers and never moves funds; `/hook-proofs` grants tiers solely from server-trusted devnet RPC with IDL-pinned account positions, and devnet signing stays blocked while `HOOK_DEVNET_DEPLOYMENT` is null, so local tests can never be presented as deployment.
- `/hook-devnet` builders (`hook-devnet.ts`) are devnet-genesis gated, require an executable hook program and the on-chain policy authority, send only after a successful simulation through the reviewed wallet flow, and label hook refusals as simulation-only, so a simulated denial is never presented as on-chain evidence.
- Hook Forge v2.2: `qlihk:db` bootstraps the QLi policy for PDA-held TransferHook authorities (Meteora DBC) only when the mint keypair co-signs with an open initial policy; `hook-dbc-devnet.ts` builders insert it directly after the single DBC pool init, enforce exact signers/program allowlist/1232-byte size and simulation success, and all new writes require a listed or owner-reviewed code fingerprint, so unknown programs or hidden first buys can never be signed.
